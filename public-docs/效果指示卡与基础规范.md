# 效果指示卡与基础规范

Houdini和Nuke采用相同的两条学习路径：从工程提取制作事实，以及从用户沟通、制作调整和效果确认中总结经验。工程、效果变体、共用方案与成功经验是不同层次，分别保留来源。

## 一个方案、多张效果卡

每个工程可对应多张效果指示卡。同一套节点方案可以共用 scheme_key，而具体效果使用不同 effect_key：

| 共用方案 | 效果卡示例 | 应分别记录的区别 |
| --- | --- | --- |
| 角色表面发射、扰动、拖尾 | 身体贴身流动能量粒子 | 贴附范围、沿表面流动、拖尾长度 |
| 同上 | 身体向外爆发能量粒子 | 发射时序、向外速度、寿命曲线 |
| 同上 | 角色能量轮廓强辉光 | 共用几何与运动，发光、曝光、运动模糊或Nuke合成不同 |

这是标注方式的示例，不代表这些效果已经出现在用户知识库中。只有工程、明确预览或用户说明支持的实际效果才建立卡片；不能修改源参数来穷举或发明变体。

每张卡用独立文本描述：标题、常用别名、对象、外观、动态、核心制作方法、参数差异、动画差异、渲染差异、合成差异、帧段/Take/版本范围、来源节点、输入依赖、复用步骤及限制。缺少证据时标为推断，不能从节点名猜出画面后冒充观察。

## 学习、检查与复用

1. `fx_learn_templates` 只完成工程归档与结构提取，返回 `effect_annotations_required` 和效果目录状态。
2. 宿主助手读取各网络、输出和明确预览，使用 `fx_annotate_template_effects` 逐张保存效果卡；每批最多50张。服务校验来源节点和预览路径，不执行DCC或改源工程。
3. `fx_review_template_effects` 可先查看未映射节点。保存复核时，列出所有已读取节点、当前卡ID，并给未归属效果卡的技术节点填写排除原因。多张卡允许共用同一节点。复核是助手检查记录，不是自动证明发现了所有潜在参数组合；卡片修改或合并新分支后需要重新检查。
4. 用户说“要做一个角色身体能量粒子”时，先 `fx_search_effects(query="角色身体能量粒子")`，按外观和运动比较结果。检索使用本地加权BM25和明确填写的别名，支持中文及英文，不调用向量模型。
5. 使用 `fx_get_effect` 查看参数/渲染差异、来源节点与步骤；按 scheme_key 可以比较共用方案的其他变体。原 `fx_search_templates` 也返回效果卡匹配，`fx_get_template` 显示标注状态。
6. 选定卡后用对应 study_id 导出原工程工作副本，核对输入、尺度、帧段、渲染器、插件与依赖，再按用户的制作请求操作副本。

卡片描述被纠正时，以 supersedes 指向当前卡，保留旧修订；新增一种表现则新增 effect_key。独立设备对同一来源、同一 effect_key 和完全相同内容的标注可折叠显示，仍保留全部来源ID。不同效果变体不因节点或方案相同而被合并；真实分歧保留分支，必须读取所有当前头后才能明确修订。

## 同一效果的对象副本与组成渲染层

不按对象编号、ROP或渲染层数量计算效果数量。“一号龙眼部橙黄能量亮点”“二号龙双眼橙黄能量亮点”“三号龙眼部橙黄能量亮点”在核实为同一效果的对象副本后，可以合为“龙眼橙黄能量亮点”。独立外观、动态或用途的变体仍分别保留，不能仅凭名称相似或节点相同判断。

Dream由宿主助手检查此类拆分，不自动批量猜测。先检索并展开完整来源卡，再调用 `fx_merge_effect_cards(card_ids, card, reason)` 预览；`apply=true` 原子写入。card使用新effect_key，总结方法并保留各层标题/别名、输出与参数差异，包含全部节点、输入、复用节点、预览和画面证据。`component_card_ids` 绑定不可变原卡；默认检索与目录显示一张总卡，原卡通过ID或 `include_history=true` 继续读取。旧卡返回 `merged_into_card_ids`，合并总卡可继续用fx_refine_effect修订，不能丢弃组成层绑定。

当前仅支持同一study内合并，拒绝过期来源或漏掉冲突头。合并不修改源工程、不升级为已验证成功经验；旧复核可能失效，需要重新核对。Dream的经验整理与卡片合并分别记录，`fx_undo_dream` 不撤销卡片合并。

总卡主模块仍最多4个；组成层的全部原模块另由服务生成 `component_modules` 保留，模块筛选同时匹配两者。制作、材质与渲染合为完整工作流时，即使来源合计超过4个模块，也不会丢失其他模块的检索入口。

效果卡默认是工程参考资料。提炼方法可用 `fx_learn_template_experience(..., effect_card_id=...)` 保存为候选；实际使用后的反馈与最终确认继续走现有学习流程。Dream整理共用方法和经验，不删除不同变体，也不把参考卡自动升级为已验证成功经验。

## 全部保存在data

| 位置 | 内容 |
| --- | --- |
| `data/memory.sqlite3` | 效果卡正文、方案关联、变体、修订、复核，以及原有经验/反馈 |
| `data/effects/` | 每张卡的独立Markdown，可从数据库重建 |
| `data/cases/` | 原工程、提取快照和精简归档 |
| `data/baselines/houdini/` | Houdini MCP原有36份Markdown，其中31份工作流，附MIT许可与NOTICE |
| `data/baselines/project/` | FX Agent当前的Houdini/Nuke及学习工作流 |
| `data/modules/global/houdini/`、`nuke/` | 基础规范索引，以及确认并最终提炼后的模块补充 |

基础规范通过 `fx_sync_module_baselines` 从当前依赖和项目同步到data，不再只有.venv中的副本。每个来源只保留houdini/project一个当前目录；更新时同步新增、修改和删除，不保留project-2等历史目录。完整SHA-256、来源和版本记录在manifest中，仅用于当前内容校验。同步成功后整合旧编号和哈希目录并更新索引。先完成临时复制与校验再替换，失败时恢复原内容；回滚也失败则保留可恢复文件并报告错误。

升级依赖或工作流后运行 `fx_sync_module_baselines`，或：

```powershell
.venv\Scripts\python.exe scripts/sync_module_baselines.py
```

原始上游规范可能含运行时模板占位符，原工具仍负责按对应版本格式化；当前规范是可独立携带、阅读和校验的基础资料，不算个人学习成果，不由Dream改写。

手动复制整个data即可携带规范与成果；先停止数据写入。代码与data仍分别管理，不需要携带旧.venv。已有另一份data时使用原有迁移/合并工具：案例和学习记录继续按原规则保留证据；基础规范则用明确导入的当前内容替换同来源目录。旧来源若只有编号快照，按数值最高后缀选一份；无法可靠区分的旧哈希目录要求先同步来源。效果文本可重建，用户已有不同文本不会被悄悄覆盖。`.baseline.lock`是临时运行锁，迁移工具不会复制它。接口保留snapshot_id/snapshots等旧字段名以兼容现有调用，它们只表示当前内容摘要，不产生历史副本。

当前基础规范、原工程事实、候选解释和已确认经验各自保留证据层次。数据库没有符合条件的最终经验时，不会伪造模块补充；README仅解释位置和状态。
